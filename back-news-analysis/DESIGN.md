# back-news-analysis 설계 문서

> `nemo-stock` 루트 `DESIGN.md` §16의 상세판. 이 디렉터리는 `backend/`·`frontend/`와 완전히
> 독립된 Python 프로젝트로, 뉴스 원문(`naver_economy_news.json`)을 AI로 분석해 종목별 백테스트에
> 쓸 수 있는 "뉴스 영향도 점수" 변수를 산출한다.

## 0. 목표

- `naver_economy_news.json`(네이버 경제 뉴스 92,229건, 2026-06-29~07-18)에서 기사 단위로 AI가
  구조화된 변수(분류/감성/영향도/관련종목 등)를 추출한다.
- 같은 사건을 다루는 여러 기사를 하나의 "이벤트"로 클러스터링한다.
- 이벤트별 영향도(strength) × 시간 경과에 따른 감쇠(decay) × 보도량 가중(count_factor)을
  결합해 특정 종목의 특정 시점 기준 최종 점수를 계산한다.
- 결과를 JSON과 SQLite 양쪽에 캐싱해, 반복 조회 시 AI를 재호출하지 않는다.
- 대량 처리는 OpenAI Batch API로 비용을 절감하고, 캐시에 없는 개별 건은 실시간 호출로 빠르게
  채운다.

## 1. 전체 흐름

```
naver_economy_news.json (92,229건)
        │
        ├─ (A) 임베딩 (text-embedding-3-small)  ──┐
        │                                          ├─► clustering.py (코사인 유사도 기반)
        └─ (B) AI 라벨링 (gpt-5.6-luna, 고정 스키마) ┘         │
                                                               ▼
                                              cache_store.py (JSON / SQLite)
                                                               │
                                                               ▼
                                          aggregate.py (decay/count_factor/정규화)
                                                               │
                                                               ▼
                                              종목별 최종 점수 (score_stock.py 데모)
```

(A)와 (B)는 기사 1건당 완전히 독립적인 요청이라 OpenAI Batch API로 대량 제출 가능(§4).
클러스터링(위 그림에서 두 결과를 합쳐 처리하는 단계)은 시간순 순회 + 기존 클러스터 목록을
갱신하는 로컬 연산이라 배치로 나눌 필요가 없다.

## 2. 기사 단위 AI 라벨링 (`scoring.py`)

뉴스 1건(제목 + 본문 최대 1500자)을 `gpt-5.6-luna`(백엔드와 동일 모델, `backend/.env`의
`OPENAI_MODEL` 재사용)에 보내 다음 고정 스키마 JSON을 받는다:

| 필드 | 의미 | 값 |
| --- | --- | --- |
| `depth1` | 뉴스 상위 분류 | 자유 텍스트 (예: 증권, 산업, 정책) |
| `depth2` | 긍/중/부정 방향 | `긍정` / `중립` / `부정` |
| `depth3` | 세부 이벤트 유형 | 자유 텍스트 (예: 실적이익, 소송, 공급계약) |
| `scope_type` | 주요 영향 범위 | `종목직접` / `업종전반` / `시장전체` |
| `related_tickers` | 직접 관련 종목 | 문자열 배열 |
| `related_industries` | 관련 업종 | 문자열 배열 |
| `impact_grade` | 영향력 등급 | 정수 1~9 (§2.1) |
| `time_horizon` | 예상 영향 기간 | `단기` / `중기` / `장기` |
| `confidence` | 분류 신뢰도 | `확실` / `보통` / `불확실` |
| `reasoning` | 분류 근거 | 자유 텍스트 1문장 |

`sentiment`(+1/0/-1)와 `magnitude`(0.2~1.8)는 각각 `depth2`/`impact_grade`로부터 **파생 계산**되며
별도 AI 호출이 필요 없다(`schemas.py`의 `@property`).

### 2.1 impact_grade — 9단계 고정 앵커 (2026-07-22 도입)

처음에는 `High`/`Medium`/`Low` 3단계였으나, "등급을 AI가 자체 판단하지 않도록" 각 등급에 구체적
예시를 명시한 9단계로 교체했다(`scoring.py`의 `_IMPACT_GRADE_TABLE`, 시스템 프롬프트에 그대로
포함):

| 등급 | 수준 | 예시 |
| --- | --- | --- |
| 1 | 극히 경미 | 유명인 근황에 기업명 스치듯 언급, 일반 통계 발표 |
| 2 | 매우 경미 | 사소한 임원 동정, 일상적 매장 오픈 |
| 3 | 경미 | 소규모 신제품 출시, 소액 계약, 목표주가 소폭 조정 |
| 4 | 통상 | 예상 부합 분기 실적, 정기 주총, 통상 인사 |
| 5 | 다소 중대 | 실적 서프라이즈/쇼크, 유의미한 신규 계약, 신용등급 전망 변경 |
| 6 | 중대 | 매출 대비 비중 큰 대규모 수주, 규제당국 조사 착수 |
| 7 | 매우 중대 | 경영진 구속/기소, 대규모 리콜, 주요 소송 패소 |
| 8 | 심각 | 분식회계 적발, 상장폐지 위기, 대규모 유동성 위기 |
| 9 | 극심각(국가적 충격) | 전쟁·내전 발발, 국가 부도, 회사 파산·청산 |

`magnitude = impact_grade / 5.0` (등급 5 = 1.0을 기준으로 선형 스케일, 범위 0.2~1.8).
스키마 자체가 바뀌었으므로 `PROMPT_VERSION`을 `v2`→`v3`로 올려 이전 캐시를 자동 무효화했다
(§5 캐시 무효화 원칙 참조).

## 3. 이벤트 클러스터링 (`clustering.py`, `embeddings.py`)

원래 요구사항은 "새 뉴스가 들어올 때마다 기존 대표뉴스들과 함께 AI(LLM)에 넣어 어디에 속하는지
판단"이었다. 이 방식은 기사 건수만큼 **서로 의존하는 순차 LLM 호출**이 필요해(이전 클러스터 목록이
매번 달라지므로), 완전히 독립적인 요청만 처리 가능한 Batch API(§4, 비용 절감의 핵심)와 근본적으로
맞지 않는다.

대신 `text-embedding-3-small` 임베딩(제목+요약, 기사당 완전히 독립적인 요청 → 배치 가능)의 코사인
유사도로 "기존 대표뉴스와 얼마나 비슷한가"를 판단한다:

1. 뉴스를 `published_at` 순으로 정렬해 하나씩 순회한다.
2. 각 뉴스의 임베딩을 기존 클러스터들의 대표(centroid = 최초 대표 기사의 임베딩)와 비교한다.
3. 코사인 유사도가 `CLUSTER_SIMILARITY_THRESHOLD`(기본 0.62) 이상인 클러스터가 있으면 그
   클러스터에 편입(멤버 수 +1, `related_tickers`/`related_industries` 합집합 갱신).
4. 없으면 자기 자신을 대표로 하는 새 클러스터를 만든다.

클러스터링 자체는 로컬 연산(임베딩 벡터 내적)이라 빠르고, AI 호출 없이 여러 번 반복해도 안전하다.
**중요 — 클러스터 누적**: `build_pool.py`/`extract_variables.py` 모두 클러스터 배정 전 캐시에서
기존 클러스터 목록을 불러와(`store.get_clusters()`) 이어받는다. 그렇지 않으면 실행할 때마다
클러스터가 초기화되어(2026-07-22 실제로 겪은 버그) 이전 실행이나 온디맨드 경로에서 만든 클러스터가
유실된다.

## 4. 대량 처리 — OpenAI Batch API (`embeddings.py`, `scoring.py`, `build_pool.py`)

임베딩과 라벨링 호출은 기사 1건당 완전히 독립적인 요청이라 Batch API(50% 할인)로 한 번에 제출한다.

### 4.1 Batch API 제약과 실제로 겪은 문제

- 배치 1건당 **최대 50,000 요청 또는 200MB(파일 크기) 중 작은 쪽**이 상한.
- **실제로 겪은 실패(2026-07-22)**: 92,229건을 4만 건씩 3개 청크로 나눠 제출했다가, scoring
  배치(본문 최대 1500자 포함) 2개가 `maximum_input_file_size_exceeded`로 실패했다. 실측 결과
  scoring 요청은 건당 약 5.3KB로, 4만 건이면 약 210MB가 되어 200MB 제한을 근소하게 초과했다.
  **교훈**: 요청 건수(50,000)보다 파일 크기(200MB)가 먼저 걸릴 수 있으므로, 페이로드가 큰 요청
  (본문을 통째로 넣는 scoring 등)은 건당 바이트 수를 실측해 청크 크기를 역산해야 한다.
  이후 청크 크기를 25,000건(≈132MB)으로 낮춰 해결했다(`build_pool.py`의 `CHUNK_SIZE`).
- 임베딩 배치는 페이로드가 훨씬 작아(건당 약 700B) 4만 건도 문제없이 처리됨 — 두 호출의 청크
  크기를 굳이 분리하지 않고 더 보수적인 쪽(25,000)에 맞춰 통일했다(코드 단순화 우선).

### 4.2 전체 코퍼스(92,229건) 처리

`build_pool.py --submit --all`이 전체 뉴스를 `CHUNK_SIZE`(기본 25,000)씩 나눠 청크마다
임베딩+채점 배치를 제출하고, 청크별 배치 ID를 `data/build_pool_all_state.json`에 기록한다.
`--poll --all`은 청크별로 완료 여부를 확인해, 완료된 청크만 그때그때 클러스터링(§3의 누적 원칙
적용)해 캐시에 반영하고 상태 파일에 완료 표시를 남긴다 — 아직 안 끝난 청크가 있어도 끝난 만큼은
반영되고, 다시 실행하면 나머지 청크를 이어서 처리한다.

### 4.3 온디맨드(캐시 미스) 경로 — 배치가 아닌 실시간 호출

백테스트 등에서 캐시에 없는 뉴스가 즉시 필요할 때(`extract_variables.py`)는 배치 turnaround(수분
~24시간)를 기다릴 수 없으므로 동기(실시간) API 호출로 즉시 채운다(`score_one`/`embed_one`).
92,229건 전체를 매번 훑지 않도록, 회사명 문자열이 실제로 제목/본문/요약에 포함된 뉴스만
후보로 추린 뒤(`candidate_url_hashes`, 무료 로컬 필터) AI를 호출한다.

## 5. 캐시 (`cache_store.py`)

- `JSONCacheStore`(`data/news_ai_cache.json`)와 `SQLiteCacheStore`(`data/news_ai_cache.db`)가
  동일한 `CacheStore` 인터페이스를 구현. `--store json sqlite`로 하나 또는 둘 다 선택 가능.
- 캐시 키는 `url_hash`(뉴스 원문의 고유 해시). `(subject, prompt_version, model)` 조합으로 캐시
  무효화하는 백엔드의 `ai_score_cache` 패턴(`backend/app/ai/scoring_cache.py`)과 동일한 사상 —
  `config.PROMPT_VERSION`을 올리면 스키마가 바뀐 캐시를 자연스럽게 무시하고 재추출한다.
- **원시 변수와 점수 계산식 분리**: 캐시에는 AI가 추출한 원시 변수(`NewsVariables`)만 저장한다.
  decay/count_factor/정규화 같은 "점수 계산식"은 조회 시점마다 `aggregate.py`가 캐시된 원시
  변수로부터 매번 다시 계산한다. 계산식이 바뀌어도(예: decay 공식 변경) 이미 캐시된 AI 호출
  결과는 그대로 재사용 가능 — 단, 원시 변수 스키마 자체가 바뀌면(예: impact 등급 체계 변경,
  §2.1) 해당 필드는 재추출이 필요하다.

## 6. 최종 점수 계산 (`aggregate.py`)

```python
strength = sentiment(+1/0/-1) * magnitude(0.2~1.8)          # 뉴스 1건의 영향도
decay(d) = 1 / (d + 1)                                       # d = 이벤트 최초 보도일로부터 경과일
count_factor = 1 + 0.3 * log(source_count)                   # source_count = 같은 이벤트를 다룬 뉴스 수
event_score = strength * decay(d) * count_factor
종목 점수 = 그 종목에 관련된 모든 이벤트의 event_score 합산 -> 평균 -> tanh로 [-1, 1] 정규화
```

- `strength`는 클러스터(이벤트) 소속 뉴스들의 개별 `strength` 평균으로 계산(`cluster_strength`).
- `d`는 이벤트의 최초 보도일(`first_published_at`)과 조회 기준일(`as_of`)의 차이. 아직 일어나지
  않은 미래 이벤트(`d < 0`)는 점수에 반영하지 않는다.
- `source_count`는 해당 클러스터의 멤버 뉴스 수(`ClusterInfo.source_count`).
- 최종 정규화는 `math.tanh`로 무한 발산을 방지해 [-1, 1] 범위를 보장한다.

## 7. 알려진 한계 / 향후 개선 지점

- 뉴스 원문에 종목 태깅이 없어, 관련 종목/업종 추출을 전적으로 AI(및 온디맨드 경로의 문자열
  사전 필터)에 의존한다. 회사의 비공식 약칭이나 신규 상장사는 놓칠 수 있다.
- 클러스터 유사도 임계값(0.62)은 경험적으로 정한 값으로, 데이터셋이 바뀌면 재튜닝이 필요할 수
  있다.
- `count_factor`의 `source_count`는 "같은 클러스터에 속한 뉴스 수"를 그대로 쓴다 — 동일 매체의
  중복 재전송 기사와 서로 다른 매체의 독립 보도를 구분하지 않는다(출처 다양성 가중치는 향후
  개선 후보).
- Batch API 제출/폴링은 CLI 수동 실행 전제(`build_pool.py --submit/--poll`). 스케줄러 연동(주기
  자동 재제출) 등은 범위 밖.
